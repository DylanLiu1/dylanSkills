AWS Bedrock 企业级解决方案全景指南

从单点模型调用到生产级 GenAI 平台：架构全景、服务分工、六大解决方案模式、八大横切关注点。中文讲解，专业术语与 AWS 服务名保留英文。

1. 全景架构总览：一套企业级 GenAI 方案由哪几层组成？

一套生产级 GenAI 方案绝不是"调一个模型 API"那么简单。AWS 的设计哲学是：以 Amazon Bedrock 为模型与 GenAI 能力中枢，周围环绕数据层、编排层、接入层、安全治理层、可观测层，每层由专门的托管服务组成，全部 serverless / managed，企业无需管理 GPU 和模型基础设施。

2. 核心引擎：Amazon Bedrock 详解

Amazon Bedrock 是全托管的 GenAI 服务：一个 API 入口，多家厂商的 Foundation Models（FM）——Anthropic Claude、Amazon Nova/Titan、Meta Llama、Mistral、Cohere、AI21 等。它不只是"模型代理"，而是一整套 GenAI 原语（primitives）的集合。下面逐个拆解。

2.1 推理 API 体系：四种调用方式怎么选

API返回方式典型场景注意点
InvokeModel一次性完整响应后台批处理、非交互任务延迟 = 完整生成时间，不适合聊天
InvokeModelWithResponseStreamtoken 级流式聊天、实时助手、长响应（15–45s）显著降低"感知延迟"，前端可逐字渲染
Converse / ConverseStream一次性 / 流式多轮对话的标准接口，跨模型消息格式统一上下文通过请求中的 messages 数组显式传递；支持 tool use
InvokeModel（Batch 模式）异步，结果写 S3大规模离线任务（万级 prompt）价格更低，但绝不能用于交互式场景
解决不同交互形态（实时聊天 / 多轮对话 / 离线批跑）用不同 API，避免"一个 API 硬撑所有场景"导致的延迟与成本失控。Converse API 还解决了"换模型就要改代码"的问题——消息格式与厂商无关。

2.2 容量模式与请求路由：钱花在哪、流量往哪走

模式计费适用关键陷阱
On-Demand按 token 计费，无固定成本流量波动大、时区型高峰、POC有账户级 TPS/TPM 配额，峰值会被 throttle
Provisioned Throughput (PT)按 Model Unit 小时计费（有固定成本）稳定高吞吐、延迟敏感、生产 SLA⚠️ 必须用 CreateProvisionedModelThroughput 返回的模型 ARN 调用，否则流量仍走 On-Demand
Cross-Region Inference (CRI) Profile按 token（同 On-Demand）削峰、容灾、数据驻留modelId 换成带地理代码的 profile ID（如 eu.amazon.nova-pro-v1:0）；SCP 需显式放行
Latency-Optimized Inference按 token（略高）不加基础设施即可压低推理延迟通过 PerformanceConfigLatency=optimized 开启
解决成本与稳定性的矛盾：波动流量用 On-Demand 不为闲置付费；稳定生产用 PT 锁定 SLA；峰值限流用 CRI 在同地理范围内自动分流——同时满足"欧洲数据不出欧洲"这类合规要求（EU 范围 profile 只路由到 EU Region）。

2.3 Knowledge Bases：全托管 RAG，一条 API 取代整条管道

Bedrock Knowledge Bases 把 RAG 的六个环节全部托管：Ingestion（S3 摄取）→ Chunking（分块）→ Embedding（嵌入）→ Vector Index（向量索引）→ Retrieval（检索）→ Context Assembly（上下文组装）。

  • 三个检索 API：Retrieve（只检索，自行拼 prompt）、RetrieveAndGenerate（检索+生成一站式，原生返回 Citations 引用）、RetrieveAndGenerateStream（流式版）。
  • 底层向量库可选：OpenSearch Serverless（大规模+元数据过滤首选）、Aurora PostgreSQL pgvector（<100 万向量、向量与元数据同库）、MemoryDB（小数据集极致召回，HNSW 索引）、S3 Vectors、Neptune Analytics（GraphRAG）。
  • 分块策略：Fixed-size（简单但断语义）、Semantic（按意义边界切，治长文档截断）、Hierarchical（父块 1000/子块 200，治跨章节引用）、Layout-aware（保表格↔文字关联）。
  • 检索增强：Reranking（内置重排，治"语义相似但上下文无关"）、Metadata Filtering（元数据收窄候选集）、Query Decomposition（复杂查询拆子查询）、Hybrid Search（向量+BM25，治精确术语漏召回）、GraphRAG（多跳实体关系）。
  • Source Attribution：每条生成内容可链接回源文档——金融/医疗/法律合规的硬需求。
解决三件事：① Hallucination（幻觉）——模型只能基于检索到的企业数据回答；② 知识时效——重跑 Ingestion Job 即更新知识，无需重训模型；③ 工程成本——不用自建 embedding 管道、向量索引与检索编排。

能力是什么解决什么
Bedrock AgentsFM + 指令 + Action Groups 的自主任务执行体，ReAct 循环（推理→行动→观察）查库存、下工单、调内部 API 等多步任务
Action Groups用 OpenAPI schema 或 Lambda 定义 agent 可调用的工具工具能力的标准化封装与权限边界
Return of Control (RoC)agent 只返回参数，由调用方自己的后端执行已有企业系统不便暴露 Lambda 时，安全接入

Code Interpretationagent 生成并沙箱运行代码数据分析、图表、计算类任务

2.5 Flows 与 Prompt Management：GenAI 工作流的工程化

  • Bedrock Flows：可视化托管工作流编排。节点类型含 Prompt 节点、Agent 节点、Knowledge Base 节点、S3 Action 节点（取/存数据）、Expression 节点（确定性解析）、Guardrail 节点。把"S3 取文件 → 抽取特定段落 → 送模型审核 → 结果写回 S3"这类流程免代码串起来。
  • Prompt Management：Prompt 的版本控制 + 审批工作流 + 变量参数化（{{variable}} 定义必填输入与输出格式）。数百个模板跨团队治理、防 prompt drift、配合 IAM 控制谁能发布、CloudTrail 全程审计。
  • Intelligent Prompt Routing：按 prompt 复杂度自动路由到大小模型——70% 简单问题走小模型省钱降延迟，30% 复杂问题走大模型保质量，零自定义分类代码。

2.6 Guardrails：推理路径上的内容安全闸门

Bedrock Guardrails 在输入与输出双侧内联执行（低延迟，可满足 200ms 级要求），六大能力：

能力干什么关键配置
Content Filtershate / sexual / violence / insults / misconduct / prompt attack（防注入）强度 low/medium/high；面向客户金融场景建议 medium，防注入用 high
Denied Topics整类话题拒绝（投资建议、保证收益）定义 + 示例短语提高检出率
Sensitive Info (PII)PII 检测与处理三种动作：block（拦截，用于输入）/ mask（打码，用于输出与测试验证）/ detect（只标记不阻断）
Word Filters自定义词表（如竞争对手名称）content filter 做不到的事交给它
Contextual Grounding验证输出是否基于给定上下文（防幻觉）高阈值 = 强制有据可依
Guardrail Profile同一护栏配置跨区域一致应用⚠️ guardrail 是 Region 级资源，数据驻留场景每 Region 部署本地副本
解决把"内容安全"从应用代码里抽出来成为平台级、可版本化、可审计的策略层。集中治理模式：CloudFormation StackSets 把 guardrail 下发到所有账户 + SCP 强制调用必须携带 guardrail ID。

2.7 Model Evaluation 与 Customization：质量与定制

  • Model Evaluation：JSONL 数据集放 S3 → 评估作业 → 结果写 S3。支持 automatic metrics（BERTScore 等）与 LLM-as-a-judge（固定同一 judge 模型保证横向可比，数值评分 1–5 可做 CI/CD 质量门禁）。RAG 场景区分 retrieve-only 与 retrieve-and-generate 两类作业。
  • Customization 三档：Fine-tuning（标注数据，改变行为/风格/格式；定制模型只能用 Provisioned Throughput 调用）、Continued Pre-training（未标注语料，注入领域知识）、Model Distillation（大模型教小模型，降本）。Custom Model Import 可把自训模型迁入 Bedrock 统一管理。
  • 决策口诀：先 RAG → 再 Prompt Engineering → 最后才微调。

2.8 Bedrock Data Automation（BDA）：多模态数据进 RAG 的传送带

Bedrock Data Automation 面向大规模多模态语料（PDF、PPT、图片、音/视频）的自动化处理编排：内部集成 Textract（文档抽取）与 Transcribe（语音转写），输出结构化摘要/概念供 FM 使用。解决"非结构化多模态数据无法直接进 RAG"的问题。

3. 六大企业级解决方案模式：每种解决什么问题、由什么组成

3.1 模式一：RAG 知识库问答（企业知识助手）

问题通用大模型不懂企业内部知识（产品手册、合规条例、临床指南、历史会话），直接问会幻觉编造；全量微调贵且知识一更新就过时。

架构组成与数据流

S3 语料 → Knowledge Bases(摄取/分块/嵌入) → 向量库(OpenSearch Serverless) 用户问题 → API Gateway → Lambda → KB RetrieveAndGenerate → 带回引用的答案 └→ Guardrails(接地校验+PII) └→ 会话状态 DynamoDB
服务在方案中的职责
S3语料源存储；版本控制、Lifecycle 过期清理（如"只引用 3 年内报告"）
Knowledge Bases托管 RAG 全管道；citations 满足可溯源审计
OpenSearch Serverless向量索引 + 混合搜索 + 元数据过滤，千万级文档免集群管理
Lambda + API Gatewayserverless 查询入口，自动扩到万级并发
Guardrailscontextual grounding 校验回答忠于检索内容；按用户角色（Cognito 组）动态选不同 PII 策略
DynamoDB会话历史/用户上下文存储，毫秒级读写、on-demand 扩容、SSE 加密
解决幻觉（只基于企业数据回答）、可审计（每条答案带引用）、知识新鲜（重摄取即更新）、权限隔离（每租户一个 KB + IAM，或 Q Business ACL）。变体：GraphRAG（Neptune Analytics）解决"投资工具↔板块↔监管"这类多跳关系问答；Hybrid Search 解决法律法条/医学缩写的精确召回。

3.2 模式二：企业级 Agent / 多智能体系统

问题业务需要 AI 不只回答、还要"办事"：查订单、建工单、跨多部门（临床/保险/预约/理赔）协作，且每个部门数据必须隔离、行为必须可审计。

架构组成与数据流

用户 → API Gateway/AppSync → Supervisor Agent(意图分类+路由) ├→ Collaborator A（临床）→ 专属 Knowledge Base + Action Group(内部 API) ├→ Collaborator B（理赔）→ 专属 Knowledge Base + Action Group(Lambda) └→ AgentCore(记忆/身份/事件) · Guardrails · Tracing 全程伴随
服务在方案中的职责
Bedrock Agents（Supervisor + Collaborator）意图路由与领域执行；新部门 = 新 collaborator，无需重构
AgentCore托管记忆、会话感知推理、身份与事件驱动执行
Action Groups / Lambda工具封装；Lambda 执行实际业务调用
API Gateway + EventBridge同步请求与事件驱动两种调用模式的注册入口
IAM（每 KB 独立授权）部门级数据隔离，杜绝跨部门泄露
Agents Tracing每步推理与工具调用可见、可审计
Step Functions（可选）对需要确定性/人工审批的关键路径做硬编排（waitForTaskToken 挂起等审批）
解决从"问答"到"执行"的跨越；多租户/多部门的数据隔离与可扩展性；agent 行为的可控（工具权限边界）与可审计（trace）。何时不用 agent：流程完全确定的任务用 Step Functions / Flows 更便宜、更可预测——agent 留给真正需要动态决策的场景。

3.3 模式三：实时流式交互（语音助手 / 逐字对话）

问题呼叫中心坐席助手要求边说边转写、端到端 <1 秒给出建议；C 端聊天要求逐字出现、数千并发长连接、响应长达 15–45 秒不能用请求-响应硬等。

架构组成与数据流

语音流 → Transcribe Streaming(partial results) → InvokeModelWithResponseStream 文本流 → API Gateway WebSocket API ⇄ Lambda → 逐 token 推送到坐席/用户端
服务在方案中的职责
Transcribe Streamingpartial results 在说话人未说完时输出片段——亚秒链路的第一环
Bedrock 流式 APItoken 级输出，生成一点推一点
API Gateway WebSocket托管双向长连接，服务端主动推送，天然支撑高并发
Lambda Response StreamingHTTP 场景下把部分响应即时吐给客户端
解决感知延迟（首 token 快 = 体验快，哪怕总时长不变）与双向实时性（替代低效轮询）。反模式：batch 转写用于实时、前端持 IAM 凭证直连 Bedrock、100ms 轮询假装流式。

3.4 模式四：文档智能处理管道（Intelligent Document Processing）

问题每日万级扫描件/PDF/视频涌入（贷款申请、财报、培训素材），要结构化抽取、去 PII、生成摘要与嵌入入库，且低置信内容要转人工。

架构组成与数据流

S3 上传事件 → Step Functions 编排： ├ 文档: Textract(结构化抽取+置信度) → 低置信 → A2I 人工复核 ├ 音视频: Transcribe 转写 文本: Comprehend(PII redaction/毒性/分类) └ 多模态大规模: BDA 统一编排 → Bedrock 生成摘要/嵌入 → 向量库
服务在方案中的职责
Textract扫描表单/表格结构化抽取，输出字段置信度
Amazon A2Ihuman-in-the-loop：低置信样本路由人工，结果回流
ComprehendPII 检测与 redaction（必须脱敏不是只检测）、toxicity、prompt safety 分类——多个检测并行调用避免串行延迟
BDA多模态（文档+音视频）统一处理编排
Glue（可选前置）大规模数据准备：crawler 编目入 Data Catalog（可审计元数据）、ETL 自定义分块、Data Quality 规则与指标
Step Functions并行编排（Parallel/Map）、重试、审计轨迹
解决非结构化数据的工业化入口：专用服务各司其职（选错服务是最大陷阱——Macie 只做静态发现、Rekognition 管图像审核、Textract 管结构抽取），人在环上兜底质量，全程事件驱动、可审计。

3.5 模式五：企业搜索与开箱即用助手（Amazon Q Business）

问题不想写代码就想要一个企业级 AI 助手：接 S3/SharePoint/Salesforce 等 40+ 数据源，且必须按员工身份过滤"你能看什么"（文档级 ACL）。

关键机制

  • Amazon Q Business：全托管企业助手，内置检索、对话与插件。
  • 文档级 ACL：S3 数据源配单一 acl.json（S3 前缀 → IAM Identity Center 组映射），查询时按用户身份过滤——IAM 权限策略替代不了这个机制。
  • Data Accessor：数据留在客户侧，授权第三方（如 ISV）受控、可撤销、可审计地检索——解决"数据所有权归客户、能力由厂商提供"的多方协作。
解决"零开发上线企业助手"与权限感知检索（AI 不能成为越权看数据的旁路）。与 Kendra 的区别：Kendra 偏传统智能搜索/FAQ，Q Business 是 GenAI 原生助手。

3.6 模式六：AI 编码助手治理（Amazon Q Developer）

问题全员用 AI 写代码后，如何强制新团队使用公司批准的内部库、算法与代码规范，且不能要求每个项目手工加配置文件？

关键机制

  • Amazon Q Developer Pro：IDE 内的代码建议、单测生成、代码审查、转型（如 Java 升级）。
  • Customization：用内部代码库训练专属定制层，建议自动对齐公司规范；集中管理、跨项目生效、更新自动传播——这正是"不做项目级修改"的解法（项目内 rules 目录都依赖开发者自觉，无法强制）。
  • IP 保护与引用追踪：建议附带来源引用，管理员可屏蔽疑似开源许可证冲突的建议。
解决AI 编码的标准化与合规：让 AI 学公司自己的代码，而不是让公司迁就 AI 的通用习惯。

4.3 内容安全与 Responsible AI

  • 纵深防御：输入侧 Comprehend（并行跑 toxicity + prompt safety + PII redaction）→ 推理侧 Guardrails（双侧内联）→ 输出侧 grounding 校验。Guardrails 指标（InvocationsIntervened 等）直连 CloudWatch 做干预率告警与公平性监测。
  • 防提示注入：prompt attack 过滤器设 high + guardrail profile 保证跨区域一致 + CloudWatch Logs 记录每次干预事件（CloudTrail 只有 API 级，粒度不够）。
  • Responsible AI 六维工具映射：fairness → SageMaker Clarify（离线偏差分析，不是实时监控）；hallucination → grounding；privacy → PII + KMS；auditability → CloudTrail + invocation logging；provenance → 数字水印 / C2PA 内容凭证。
  • 人工兜底：Amazon A2I 按置信度路由高风险交互；或 Step Functions waitForTaskToken 挂起工作流等人工审批（SendTaskSuccess 继续），审批记录落 DynamoDB 可审计。

4.6 韧性与灾难降级（Resilience & Graceful Degradation）

  • 区域性故障/限流降级：Cross-Region Inference Profile 在同地理范围内自动把流量转移到可用 Region——免自建 failover 逻辑、无固定成本，是 Bedrock 原生的"灾难降级"方案。
  • 重试三件套：指数退避 + Jitter + Circuit Breaker（熔断器）。固定延迟重试会造成同步重试风暴；熔断器在错误率超阈值时暂停重试，防止压垮服务、实现优雅降级。流式场景缓冲已收 chunk、断点续传。
  • 追踪定位：X-Ray 全链路追踪 + annotations 标注模型特征（model ID/参数/Region），按模型维度关联延迟问题。
  • 发布级回滚：AppConfig 自动回滚（配置错误）+ Step Functions 金丝雀回滚（版本错误）+ Prompt Management 版本回退（prompt 错误）——三层回滚覆盖三类变更。
  • SageMaker 侧（自托管模型时）：最小实例数 >0 消灭冷启动、模型预热、动态批处理；异步推理只用于非交互负载。
